SESSION FIX — sign-in no longer immediately bounces back to login

Round 1 — sessions moved off Workers KV:
- Login sessions were originally stored in Cloudflare Workers KV.
- KV is only "eventually consistent" — a value you just wrote is not
  guaranteed to be readable again for up to 60 seconds, even from the
  same location.
- Fix: sessions were moved to D1 (a real SQL database, already used
  elsewhere in this project).

Round 2 — D1 read replicas were still stale:
- D1 has its own "global read replication" feature. Even in D1, a plain
  read can be served by a nearby read replica that hasn't caught up to a
  write that just happened a moment ago on the primary database — the
  same kind of lag as the KV issue, one layer down. This is why sign-in
  still bounced straight back to login after moving sessions to D1.
- Fix: the session check now uses D1's Sessions API
  (env.DB.withSession("first-primary")), which forces that read to go to
  the primary database instead of a possibly-stale replica. A session is
  now guaranteed visible the instant it's created, regardless of whether
  read replication is on for this database.

Other fixes bundled in:
- Added the missing POST /api/auth/logout route (the sign-out
  confirmation page was already calling it, but it didn't exist, so
  clicking "Sign out" there never actually cleared your session).
- The plain /logout link and Google sign-in now also properly delete the
  D1 session row on logout / create it via the same helper.

Workers KV is still used for Google Drive tokens and OAuth state, since
those aren't read back milliseconds after being written.

Deploy/upload:
1. Replace your GitHub project files with this ZIP's contents.
2. Deploy the Worker again (wrangler deploy).
3. No manual DB migration is required — the sessions table is created
   automatically. migration-sessions.sql is provided if you prefer to
   run it yourself.
